# 拡張・本番運用プラン

現在の実装は、単一サーバー上で共有パスワード・SQLite・永続ボリュームへ原本保存を行います。少人数での利用を始める構成と公開手順は [README](../README.md) を参照してください。以下は個人別ログインや大容量運用へ拡張する場合の案です。

## おすすめ：PWA + Supabase

最初はApp Store / Google Playへの申請が不要な **PWA** として公開します。家族は共有URLを開き、iPhoneなら「ホーム画面に追加」、Androidなら「アプリをインストール」で通常のアプリに近い感覚で使えます。

| 役割 | サービス | 理由 |
| --- | --- | --- |
| Webアプリ | Next.js + Vercel | Android / iPhone / PCを1コードで対応 |
| 認証 | Supabase Auth | 招待メール、Magic Link、Apple/Googleログインに対応 |
| データ | Supabase Postgres | アルバム、メンバー、写真情報を管理 |
| ファイル | Supabase Storage | 画像と短い動画を非公開バケットに保存 |
| 画像処理 | Cloudflare Images（後から） | サムネイル生成と通信量削減 |
| 長い動画 | Cloudflare Stream / Mux（後から） | 自動変換し、端末を問わず再生しやすくする |

## 絶対に入れる安全設計

- ファイルを公開URLにせず、ログイン済みメンバーだけに短時間の署名付きURLを発行する。
- DBのRow Level Securityで「所属アルバムのデータだけ」を取得可能にする。
- アルバム参加は、期限と一度きりのトークンを持つ招待リンクにする。
- アップロード時にMIMEタイプ、拡張子、容量をサーバーでも検証する。
- 元画像は保持し、一覧では軽量なサムネイルを使う。EXIF位置情報は初期設定で削除する。
- 削除は30日間のゴミ箱を経由し、DBとストレージを毎日バックアップする。

## 最初のリリースに入れる機能

1. メールのMagic Linkログイン
2. アルバム作成と家族の招待
3. 写真・動画の複数アップロード（バックグラウンド再試行付き）
4. 月別タイムライン、全画面表示、端末へのダウンロード
5. 撮影者と撮影日時の表示
6. ゴミ箱と退会
7. アルバム単位のPCバックアップと復元

コメント、いいね、顔認識、自動アルバム、テレビ表示は利用状況を見て第2段階で追加します。最初に機能を増やしすぎず、「追加・見る・保存」の3操作を確実にするのが重要です。

## サーバー容量の考え方

必要容量は、ほぼ「動画の長さ」で決まります。まずは次の式で見積もります。

```text
必要容量 = 写真枚数 × 写真1枚の平均容量
         + 動画分数 × 動画1分の平均容量
         + サムネイルなど（原本容量の約10%）
```

仮に写真を1枚4MB、スマホ動画を1分100MBとして計算すると、写真1,000枚で約4GB、動画100分で約10GBです。これにサムネイルと余裕を加えた **約16GB** が目安になります。これは画質や端末設定で大きく変わるため、本番前に実際のファイル50〜100個の平均値を測ります。

家族4人が毎月「写真100枚＋動画10分」を追加する例では、月約5.6GB、年約67GB、3年で約200GBです。運用開始時は100GB程度から始め、使用率が70%を超えたら次の容量へ増やす設計が現実的です。アプリ画面には使用量・上限・残量を常に表示し、80%で管理者へ通知します。

容量を抑える場合も、元画像を勝手に圧縮せず、次を優先します。

- 一覧表示には200〜500KB程度のサムネイルだけを配信する。
- 動画はストリーミング用に変換しても、原本を残すかどうかをアルバム設定で選べるようにする。
- 重複ファイルをハッシュで検出し、同じ原本を二重保存しない。
- ゴミ箱を30日後に自動削除し、不要な一時アップロードを定期的に掃除する。

## PCバックアップ設計

現在の画面では、サーバーにある全写真・動画の原本と `tokiha-backup.json` を1つの `.tar` ファイルにまとめて保存できます。サーバーの永続ボリューム全体も別の場所へ定期的にバックアップしてください。

大容量を扱う版では、バックアップを非同期ジョブにする設計が考えられます。

1. バックアップ要求をジョブとして登録し、その時点のファイル一覧を固定する。
2. ストレージから原本を順に読み、撮影日時や投稿者を含むJSONと一緒にZIPへ格納する。
3. 完成後、24時間だけ有効な署名付きダウンロードURLをメールと画面で通知する。
4. ダウンロード用ZIPは期限後に自動削除し、アルバム本体の容量へ加算しない。
5. 大容量の場合は10〜20GBごとに分割し、失敗した部分だけ再取得できるようにする。

加えて、管理者が自宅のPCやNASへ定期同期できる読み取り専用APIを用意すると安全です。クラウド障害や誤削除に備え、クラウド内バックアップだけでなく、別の場所へ原本を最低1コピー保持します。

### PC自動バックアップ

ブラウザには、利用者の操作なしにPCのフォルダへファイルを書き込む権限がありません。そのため自動保存は、付属のPC用クライアントを一度だけ設定し、その後は **Windows / macOS / Linuxへのログイン時に自動実行**します。

```bash
python3 scripts/install_tokiha_backup.py \
  --server-url https://your-tokiha.example \
  --destination ~/Pictures/TOKIHA
```

インストーラーはOS標準のログイン時起動（Windows Startup、macOS LaunchAgent、Linux autostart）へ登録します。クライアントはサーバーの `/api/v1/backup/manifest` を確認し、新規・更新ファイルだけを `撮影年/撮影月` フォルダへ保存します。SHA-256が一致した場合だけ完了扱いにするため、通信が途中で切れても壊れた原本を残しません。

現在のトークンはサーバー全体の原本読み取り専用です。失効にはサーバーの環境変数を変更して再起動します。アルバム単位の発行・失効画面は今後の実装です。PCを家族と共用する場合はOSのユーザーアカウントを分け、保存先ドライブの暗号化も案内します。

## 撮影日を基準にした表示

- JPEGはEXIFの `DateTimeOriginal` を読み取り、アップロード日時ではなく撮影日時として保存します。
- HEICや動画はサーバー側でメタデータを解析し、取得できない場合だけファイル更新日時、最後にアップロード日時へフォールバックします。
- 一覧は撮影日の新しい順で、`2026年9月` のような月見出しに分けます。撮影日が誤っている場合は、利用者が後から修正できるようにします。
- タイムゾーンを撮影日時と別に保存し、旅行先で日付がずれないようにします。

## デジタルデバイドを減らす仕様

- 最初の画面で「追加・見る・PCに保存」の3操作だけを案内し、設定項目は別画面へ分けます。
- アイコンだけに頼らず、常に日本語ラベルを併記します。主要ボタンは高さ48px以上を確保します。
- 専門語ではなく「アップロード」を「写真を追加」、「エクスポート」を「PCに保存」と表記します。
- 初回だけ家族が対面または電話で設定できるよう、招待リンクからログインまでを1画面ずつ案内します。
- 文字拡大、OSのダークモード、キーボード操作、スクリーンリーダー、色覚特性に対応します。
- 誤操作は即時確定せず、削除は30日間取り消せるようにします。通信が切れても自動で再開し、同じ写真を二重登録しません。
- 家族の「管理者」が代理で招待、容量確認、バックアップ状況の確認を行える一方、本人の写真を勝手に削除できない権限設計にします。

## 代替案

### 最短・運用ほぼ不要：Google Photos / iCloud共有アルバム

開発せず今すぐ始められます。ただし両OS間の体験や動画品質、アカウント管理に制約があり、独自UIにはできません。

### ネイティブ感重視：Flutter + Firebase

1コードでiOS / Androidアプリを作れ、通知やバックグラウンドアップロードに強い構成です。一方でストア審査、開発者登録、リリース管理が必要です。

### 自宅で管理：Immich

NASや小型サーバーにセルフホストできます。容量単価とプライバシーに優れますが、障害対応、外部公開、バックアップ、セキュリティ更新を自分で継続する必要があります。

## 実装の順番

- **第1週:** 認証、アルバム、権限設計
- **第2週:** 画像・動画アップロード、サムネイル、一覧
- **第3週:** ダウンロード、招待、ゴミ箱、PWA化
- **第4週:** 実機テスト、通信不良時の再試行、監視、公開

本番前に、対象人数、1人あたりの月間アップロード量、動画の最大時間、元画質保存の要否を決めるとサービス選定と費用見積もりができます。
